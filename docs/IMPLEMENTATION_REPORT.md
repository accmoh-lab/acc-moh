## ملخص تنفيذي

- **الوضع السابق:** المستودع كان يحتوي على وحدة Odoo (`acc_meeting`) لم تُشغَّل ولم تُختبر قط. الوحدة تحتاج Odoo.sh أو تثبيتًا محليًا (On-premise)، وتعتمد على مستخدمي Odoo.
- **سبب التغيير:** هذا يتعارض مع شرط الاستقلال عن Odoo. لذلك بُني **Web App مستقل** داخل المجلد `app/`. وحدة Odoo بقيت كما هي للمرجعية ولم تُحذف.
- **ما تم:** دورة الإدارة تعمل الآن من البداية إلى النهاية في المتصفح:
  - KPI ← Management Attention ← اجتماع ← تحضير ← جلسة حية ← قرار ← مهمة ← دليل ← اعتماد ← أداء ← Snapshot تاريخي.
- **الاختبارات:**
  - 17 اختبار API يتحقق من الأمان وسلامة البيانات وسير العمل.
  - 19 خطوة End-to-End في المتصفح، بأدوار Employee وManager وExecutive وBoard وMobile.
  - اختبار حمل: 600 موظف و30,000 مهمة.
  - **كل الاختبارات ناجحة.**
- **ما يحتاج قرارًا منكم:** طريقة احتساب التقييم النهائي، وشرائح التقييم، وحدّ الانحراف المالي، وسياسة سرية المجلس. كلها الآن **قيم تجريبية قابلة للضبط**، وموضحة في القسم I.

## C. البنية (Architecture)

```
Frontend (SPA عربية RTL — ES Modules بلا Build، خط عربي مستضاف ذاتيًا)
   ↓ JSON API + Session Cookie (HttpOnly, SameSite) + ترويسة CSRF
Backend/API (Node.js 22)
   ├─ Domains منفصلة: org, meetings, tasks, kpis, targets, initiatives,
   │  perf, mgmt, misc, imports, reports
   └─ Authorization داخل الخادم: RBAC + Scope
   ↓
Database (SQLite حاليًا عبر node:sqlite + Migrations بلغة SQL)
   → PostgreSQL في المرحلة التالية
   ↓
File Storage (مجلد محلي محمي بالصلاحيات) → Object Storage لاحقًا
   +
Integration Layer: app/src/integrations (Adapters بحالة معلنة)
```

**ملاحظات على اختيار التقنية:**

- **بلا حزم npm خارجية:** يقلل مخاطر Supply Chain ويبسّط التشغيل.
- **SQLite بدل PostgreSQL:** اخترته لأن بيئة العمل لا تحتوي خادم PostgreSQL.
  - الـSchema مكتوب بلغة SQL متوافقة، ويستخدم Foreign Keys وCHECK وIndexes.
  - الانتقال إلى PostgreSQL هو أول توصية Critical في القسم J.
- **الأتمتة (T-48h والتنبيهات):** تعمل داخل الخادم كل دقيقة، وهي Simulation معلنة.
  - في الإنتاج تُنقل إلى Worker أو Scheduler منفصل.
- **المصادقة:** مستقلة تمامًا عن Odoo.
  - كلمات المرور مشفرة بـscrypt.
  - Rate limiting، وقفل الحساب بعد 5 محاولات فاشلة، وسياسة لكلمة المرور.
  - تحقق TOTP جاهز في الخادم (MFA). لا توجد بعد شاشة لتسجيل الجهاز.
  - SSO جاهز في البنية لكنه غير مربوط.
- **الأمان:**
  - ترويسات: CSP وX-Frame-Options وnosniff، وHSTS عند تفعيل `HTTPS=1`.
  - الأسرار عبر متغيرات البيئة (`.env.example`)، ولا أسرار داخل المستودع.
- **التشغيل:** يوجد `Dockerfile` ونقطة فحص صحة `/api/health`.

## D. قاعدة البيانات — أهم الكيانات والعلاقات

**التنظيم والصلاحيات:**
- `org_units` — شجرة: Group ← Company ← BU ← Department ← Team.
- `employees` — تحمل الوحدة والمدير المباشر والمدير الوظيفي والدور الأساسي ونطاق الوصول.
- `employee_grants` — أدوار وظيفية إضافية ونطاقات إضافية.
- `sessions` و`password_resets`.

**الاجتماعات:**
- `meetings`: الحالة، والسرية، والتكرار عبر `series_id`، وحزمة التحضير المجمّدة `prep_pack`.
- `meeting_participants`: الدعوة والحضور وطريقة الحضور.
- `agenda_items`: مرتبطة بـKPI وبالقرار.
- `minutes`: تحفظ Snapshot الحضور الفعلي عند الاعتماد.
- `meeting_kpis` و`attachments`.

**القرارات والمهام:**
- `decisions`: ترقيم `DEC-YYYY-####`.
- `tasks`: تحمل المصدر وروابطها (اجتماع، قرار، بند، KPI، مبادرة)، والاعتماد، والسرية، والتكرار.
- `task_dependencies` (مع منع الحلقات الدائرية)، و`task_evidence`، و`task_events` لسجل كل تغيير.

**المؤشرات والأهداف:**
- `kpis`: النوع، والعتبات، والصيغة، والأب، وطريقة التجميع (Rollup).
- `kpi_results`: سجل مستقل لكل فترة، يحمل جودة البيانات.
- `financial_targets` (مع العملة) و`fx_rates`.

**الأداء:**
- `performance_periods`: الحالة، والإصدار، وعدد مرات إعادة الفتح.
- `period_snapshots`: Snapshot مستقل لكل إصدار.
- `period_adjustments`.
- `scorecard_configs`.
- `assessments` و`assessment_stages`.
- `checkins`.

**المبادرات:** `initiatives` وجداول الربط مع KPIs والاجتماعات والقرارات.

**الإشعارات والتدقيق:**
- `notifications` (مع dedupe_key) و`notification_prefs`.
- `outbox`: البريد وPush بوضع Mock.
- `audit_log` و`automation_runs`.

**قواعد عامة:**
- كل المفاتيح IDs رقمية ثابتة، ولا تُستخدم الأسماء كمفاتيح.
- Timestamps على كل الجداول الأساسية، و`deleted_at` جاهز لـSoft Delete.

## E. الأمان

**RBAC:**
- سبعة أدوار أساسية: Employee، وTeam Leader، وDepartment Manager، وBU Manager، وExecutive، وHR Admin، وSystem Admin.
- أدوار وظيفية إضافية: Board Member، وBoard Secretary، وKPI Owner، وData Owner، وPerformance Reviewer، وMeeting Leader، وMeeting Secretary.

**Scope:**
- كل دور مقيّد بنطاق تنظيمي (شجرة فرعية)، مع إمكانية منح نطاق إضافي صريح.
- كل القوائم تُفلتر بـSQL داخل الخادم.
- أي سجل خارج النطاق يُرجع 404، حتى لا يُكشف أنه موجود أصلًا.

**Board:**
- الاجتماعات والقرارات والمستندات والمهام بسرية Board لا يراها إلا من يحمل دور المجلس.
- دور المدير وحده لا يكفي.
- مدير النظام لا يملك وصولًا إلى بيانات المجلس.

**خصوصية الأداء:**
- التقييمات وتعليقات المدير يراها فقط: سلسلة الإدارة المباشرة، والمدير ضمن نطاقه، وHR، والمراجع المعيّن.
- المشارك في اجتماع لا يرى تقييم زميله.
- الموظف يرى ملاحظات المدير **بعد الاعتماد النهائي فقط**. التعليق الداخلي لا يظهر له أبدًا.
- مدير النظام لا يرى بيانات الأداء (فصل المهام).

**التدقيق (Audit):** يُسجَّل المستخدم والوقت والقيمة القديمة والجديدة والسبب، في الحالات التالية:
- المستهدف والفعلي.
- الصيغة والوزن.
- الأوزان والتقييم.
- مسؤول المهمة وموعدها وحالتها.
- إعادة فتح الفترات والاعتمادات.
- الصلاحيات.
- الدخول، والتصدير، والاستيراد.

**الحماية التقنية:** CSRF بترويسة إلزامية، وCookie من نوع HttpOnly، وRate limiting، وقفل الحسابات، ورسائل خطأ مفهومة دون تفاصيل تقنية (المرجع التقني يُكتب في السجل فقط).

## F. سير العمل (Workflows)

**الاجتماع:**
- Draft ← Preparation (إرسال الدعوات) ← Preparation Published ← Ready ← Live ← Minutes Draft ← Under Review ← Approved ← Closed، مع إمكانية Cancelled قبل البدء.
- الانتقال غير المنطقي يُرفض بخطأ 409.
- **الحزمة:** نشرها يتطلب هدفًا وبندًا واحدًا على الأقل.
- **الإتاحة:** تُتاح للمشاركين قبل الاجتماع بـ48 ساعة، تلقائيًا عبر الأتمتة.
- **إنهاء الاجتماع:** يتطلب تسجيل حضور المشاركين الأساسيين.
- **اعتماد المحضر:** لقائد الاجتماع فقط، ويحفظ سجل الحضور الفعلي.

**المهمة:**
- Not Started ← In Progress ← (Pending Review) ← Completed، مع Blocked وCancelled.
- الوصول إلى 100% لا يعني الاكتمال.
- المهمة التي تتطلب اعتمادًا تمر بـ: تسليم ← المراجع ← اعتماد أو إرجاع بسبب.
- الدليل (Evidence) إلزامي إذا طُلب.
- لا يمكن البدء أو الإكمال قبل اكتمال المهام التي تعتمد عليها المهمة.
- المهام المتكررة تولّد Occurrence جديدًا مع الاحتفاظ بالسجل السابق.

**KPI:**
- جودة البيانات: Missing ← Draft ← Submitted ← Verified ← Approved، مع إمكانية الإرجاع.
- فصل المهام: من أدخل البيانات لا يتحقق منها.
- **البيانات المحتسبة رسميًا** في الأداء هي Verified وApproved فقط.
- **المؤشرات المشتقة** (Formula وRollup) تُعاد حسابتها تلقائيًا.

**الأداء:**
- Open ← Under Review ← Approved ← Locked.
- الاعتماد يتطلب الإقرار الصريح بالفجوات إن وُجدت.
- الإقفال يحفظ Snapshot لكل موظف ووحدة.
- إعادة الفتح تتطلب سببًا وتنشئ إصدارًا جديدًا مع الاحتفاظ بالإصدار السابق.

**الاعتماد والمعايرة:**
- Manager Review ← Department Review ← Management Calibration ← Final Approved، مع إمكانية الإرجاع بسبب وسجل كامل.

## I. تحليل الفجوات (Gap Analysis)

### Features ناقصة أو جزئية

- **Deliverables:** مكوّن مستقل في Scorecard غير منفذ (Planned)؛ المهام تغطيه حاليًا.
- **المساهمون في المهام (Contributors):** الحقل مدعوم في الـAPI، ولا توجد واجهة لإضافتهم.
- **المرفقات:** تُرفع حاليًا على مستوى الاجتماع والمهمة فقط، وليس على مستوى بند الأجندة (الخادم يدعمها).
- **تكرار الاجتماعات:** أسبوعي أو شهري فقط، ويُنشأ الموعد التالي بزر وليس تلقائيًا.
- **التنبيهات:** لا يوجد Digest يومي. منع التكرار مطبّق، لكن لا يوجد تجميع.
- **MFA:** لا توجد شاشة لتسجيل الجهاز.
- **التقارير:** لا يوجد تصدير PDF من الخادم، والمتاح هو الطباعة من المتصفح.

### قرارات Business تحتاج اعتمادكم (حاليًا قيم تجريبية قابلة للضبط)

1. **شرائح التقييم:** حاليًا 110 / 100 / 85 / 70.
2. **سقف الإنجاز المحتسب:** حاليًا 120%.
3. **درجة المهام:** حاليًا 100 في الموعد، و70 متأخرة الإنجاز، و0 متأخرة مفتوحة، و85 بانتظار المراجعة.
4. **من يعتمد التقييم النهائي:** حاليًا Executive وHR.
5. **حدّ الانحراف المالي الكبير:** حاليًا 10%.
6. **سياسة سرية المجلس:** حاليًا الأعضاء وأمين السر، والمدعوون للاجتماع فقط، مع منع المستندات عن غير الأعضاء.
7. **احتساب درجة وحدة النشاط:** حاليًا تحتسب مؤشراتها المباشرة ومهام موظفيها، ومتوسط الوحدات التابعة يُعرض بجانبها. هل تُدمج الدرجتان؟
8. **مهلة إدخال بيانات KPI:** حاليًا 5 أيام بعد نهاية الفترة.

### مخاطر أمنية متبقية

- **Rate limiting:** يعمل في ذاكرة الخادم، ولا يكفي عند تشغيل أكثر من خادم.
- **الملفات المرفوعة:** لا يوجد فحص فيروسات.
- **مفاتيح التشفير:** لا يوجد تدوير (Rotation) مُدار.
- **جلسات المستخدم:** تُلغى فورًا عند تغيير الدور. لكن لا يوجد إنهاء تلقائي للجلسات الخاملة سوى انتهاء المدة (8 ساعات).

### الدين التقني

- SQLite قاعدة بيانات لكتابة واحدة في الوقت نفسه (Single-writer).
- الأتمتة تعمل داخل نفس عملية الخادم.
- إقفال الفترة يحسب الـSnapshots بشكل متزامن، وهذا يحتاج Background Job عند آلاف الموظفين.
- تسميات الحالات مكررة بين الواجهة والخادم.

### مخاطر قابلية التوسع

- حساب Scorecards الحي يعتمد على Cache قصير المدة (20 ثانية).
- لوحات المؤسسات الكبيرة تحتاج جداول تجميع (Materialized) بعد PostgreSQL.
- يجب نقل المرفقات إلى Object Storage.

## J. المرحلة التالية المقترحة

**Critical**
1. الانتقال إلى PostgreSQL، مع نسخ احتياطي يومي واستعادة مُختبَرة.
